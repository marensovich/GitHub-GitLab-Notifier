# MAX Adapter Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Post GitHub/GitLab notifications to MAX group chats and dialogs and run every chat command there,
including the personal DM commands, on top of the 2.0 messenger core.

**Architecture:** A new adapter `internal/messenger/max` implements `messenger.Messenger`, `MemberChecker` and
`DirectMessenger` with plain `net/http` against the MAX Bot API. Updates come from a webhook subscription to
`POST /max/updates` when `server.public_url` is HTTPS on port 443, otherwise from long polling `GET /updates`.
Notifications render as HTML text (`format: "html"`) with link buttons in an `inline_keyboard` attachment.

**Tech Stack:** Go 1.27 standard library only; no MAX SDK.

**Spec:** `docs/superpowers/specs/2026-11-17-v2-foundation-design.md` (sections "Commands in the core",
"Rendering per messenger", "Configuration"; card NTF-50) and
`docs/superpowers/specs/2026-11-26-personal-dms-design.md` (DM commands).

## Facts from the MAX Bot API (dev.max.ru, read 2026-11-26)

- Header `Authorization: <token>` (no prefix); query tokens are not accepted.
- The docs name `https://platform-api2.max.ru`, whose certificate is issued by the Russian Trusted CA, which Go
  does not trust by default; `https://platform-api.max.ru` answers the same API with a HARICA certificate.
- `POST /messages?chat_id=` (or `?user_id=`), body `text` (≤ 4000 chars), `format: "html"`, `attachments`,
  `link {type:"reply", mid}`, `notify`; HTML tags `b strong i em u ins s del code pre a blockquote mark h1-h4`.
  `PUT /messages?message_id=` edits; `DELETE /messages?message_id=` deletes (in a dialog only the bot's own).
- Keyboard: `{"type":"inline_keyboard","payload":{"buttons":[[...]]}}`; ≤ 7 per row, ≤ 3 when a row has a
  `link` button; `callback` buttons carry `payload` ≤ 1024 chars.
- `POST /answers?callback_id=` with `message` (replaces the pressed message) and/or `notification` (a one-time
  notice to the presser). No ephemeral messages, no alert dialogs, no threads.
- `GET /updates?marker=&timeout=&types=` → `{updates, marker}`; `POST /subscriptions {url, update_types, secret}`,
  delivered with header `X-Max-Bot-Api-Secret`, HTTPS on 443 only; polling and a webhook cannot run together.
- Updates: `message_created {message{sender{user_id,username}, recipient{chat_id, chat_type}, body{mid,text},
  link}}`, `message_callback {callback{callback_id,payload,user}, message}`, `bot_started {chat_id, user}`.
- `GET /chats/{id}` (`title`, `type`); `GET /chats/{id}/members?user_ids=` → `{members:[{user_id,is_admin,
  is_owner}]}` (the bot must be a chat administrator); `PATCH /me/commands {commands:[{name,description}]}` ≤ 32.
- Errors: HTTP 4xx `{code, message}` (`not.found`, `chat.denied`, `proto.payload`…), some methods answer 200 with
  `success:false`; 429 is the rate limit; 2 messages per second per chat.

## Global Constraints

- No MAX SDK and no new dependency.
- The Telegram and Discord goldens must not change.
- The core (`commands`, `outbox`, `server`, `storage`, `web`) imports no adapter package.
- The token never appears in an error text, a log line or a URL; `/link` arguments never reach the log.
- Default API base `https://platform-api.max.ru`; `messengers.max.api_url` overrides it.
- Commit style: Angular subject without scope, detailed English body, `Refs NTF-50.`, no attribution trailers.
- Tests run with `go test ./...`, no network (an `httptest` server stands in for MAX).

## Decisions (rulings made while planning)

1. API base `platform-api.max.ru` by default — works with the system CA bundle; `api_url` lets an owner whose
   system trusts the Russian CA use `platform-api2`. Cost if wrong: MAX retires the old host and the default
   breaks until `api_url` is set.
2. Webhook when `public_url` is `https://` with no port or `:443`, polling otherwise. Polling deletes the bot's
   subscriptions first (they cannot coexist). The webhook secret is derived from the token
   (`hex(sha256("max-webhook:"+token))[:40]`), so there is no new config key.
3. The webhook endpoint checks the secret in constant time (wrong or missing → 401, core not called), answers
   200 at once and processes the update in a goroutine.
4. Dialogs are private chats (`IsPrivate`); channels are ignored (no commands, never a destination in 2.0).
5. No ephemeral replies exist in MAX: replies are ordinary messages; a reply with buttons quotes the command
   (`link.type = "reply"`) so a press is matched to the command's sender through `message.link.sender`.
6. `Edit` answers the callback with `message` (one call edits and stops the spinner); `Answer` with text sends a
   `notification`; `Answer("")` after an `Edit` of the same press is a no-op; `alert` is ignored.
7. `IsChatAdmin`/`IsMember` read `GET /chats/{id}/members?user_ids=`; in a dialog the user is its admin. The
   bot has to be a chat administrator in groups — README says so.
8. `DirectChat` returns the dialog chat ID learned from that user's dialog updates (`message_created` in a
   dialog, `bot_started`); unknown → error (core answers `link_no_dm`). `/link` is only allowed in a dialog, so
   it is always known by then.
9. MAX does not let a bot delete a user's message in a dialog: `DeleteCommand` tries and returns the error; the
   core then adds `link_delete_token` ("delete the message with your token yourself") to its answer.
10. HTML length is checked on the HTML sent (runes ≤ 4000) — the docs do not say how MAX counts.
11. Caps: no threads, one look, `ButtonsPerRow: 3`, `PerChatRate: 2`, `PerChatBurst: 2`, `GlobalRate: 25`
    (the docs give no global limit).
12. Command menu: one list in the default language (MAX has no per-language menu).

## Review Focus

1. A webhook request with a missing or wrong `X-Max-Bot-Api-Secret` — 401, core never called (Task 4).
2. `/link github ghp_…` in a dialog: the token is never logged; the delete fails and the answer says to delete
   it by hand; in a group `/link` is refused (Task 5).
3. A press on a reply in a group by someone other than the command's sender is refused by the core because
   `OriginUserID` is filled from `message.link.sender` (Task 3).
4. Commit messages with `<`, `&`, 3000 characters or 300 commits stay within 4000 runes and only use allowed
   tags (Task 2 goldens).
5. MAX answering 200 with `success:false`, 404, 403, 429 with and without `Retry-After`, or 5xx with no body —
   each maps to the right messenger error (Task 1).
