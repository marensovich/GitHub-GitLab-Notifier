# Discord Adapter Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Post GitHub/GitLab notifications to Discord text and forum channels and run every chat command there as
slash commands, on top of the 2.0 messenger core.

**Architecture:** A new adapter `internal/messenger/discord` implements `messenger.Messenger` with plain
`net/http` against the Discord REST API (v10) and an HTTP interactions endpoint `POST /discord/interactions` on
the existing public server, verified with `crypto/ed25519`. Notifications render as one embed plus link buttons.
Forum channels get one post per event type; the core learns that a forum has no main chat.

**Tech Stack:** Go 1.27 standard library only (`net/http`, `crypto/ed25519`, `encoding/json`); no Discord SDK.

**Spec:** `docs/superpowers/specs/2026-11-17-v2-foundation-design.md` (sections "Commands in the core",
"Rendering per messenger", "Outbox", "Configuration"; cards NTF-51).

## Global Constraints

- No Discord SDK and no new dependency; signatures with `crypto/ed25519`.
- The Telegram goldens (`internal/handler/testdata/**/*.golden`) must not change.
- The core (`commands`, `outbox`, `server`, `storage`, `web`) imports no adapter package.
- An interaction is acknowledged within 3 seconds: the HTTP handler answers first and runs the core afterwards.
- Discord REST base `https://discord.com/api/v10`; header `Authorization: Bot <token>`; the token never appears
  in an error text, log line or URL.
- Every message sets `allowed_mentions: {"parse": []}` — event text never pings anyone.
- Owner's decision: wherever a messenger can show a message only to the user who sent the command, command
  replies use it. In Discord every command reply, follow-up, edit and press answer is ephemeral (flags 64).
  Telegram has no such message and keeps its replies as they are. Personal notifications in DMs (mentions,
  assignments, review requests) are a separate design after this plan.
- Commit style: Angular subject, detailed English body, `Refs NTF-51.`, no attribution trailers.
- Tests run with `go test ./...`, no network.

## Review Focus

1. A slow core (DB lock, many subscriptions) while Discord waits for the interaction answer — the endpoint must
   answer `5`/`6` at once, never after the work (Task 4 test with a blocking handler).
2. A request with a missing, malformed or wrong `X-Signature-Ed25519`, or a body changed after signing — `401`,
   and the core is never called (Task 2 and Task 4 tests).
3. A forum post that was deleted — the outbox falls back, the adapter says the forum needs a post, and the post
   for that event type is recreated once (Task 1 and Task 5 tests).
4. Commit messages and titles containing `@everyone`, `<@id>`, markdown or 3000 characters — no ping, no broken
   formatting, embed within every limit (Task 3 tests).
5. `/configure` or `/connect` typed in a thread of a text channel, in a forum post, or in a DM — acts on the
   parent channel; a DM is answered that the bot works in server channels (Task 4 tests).
